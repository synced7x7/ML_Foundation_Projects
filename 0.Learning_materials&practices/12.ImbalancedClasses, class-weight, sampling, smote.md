
# 1. Why Accuracy is Misleading for Imbalanced Classes

## Example: Fraud Detection

Suppose you have **1000 transactions**.

| Class   | Count |
| ------- | ----: |
| Genuine |   990 |
| Fraud   |    10 |

The dataset is highly imbalanced.

---

## Model A

The model predicts **every transaction as Genuine**.

Confusion Matrix

|                | Pred Genuine | Pred Fraud |
| -------------- | -----------: | ---------: |
| Actual Genuine |          990 |          0 |
| Actual Fraud   |           10 |          0 |

Accuracy

[
\frac{990}{1000}=99%
]

Wow!

**99% accuracy!**

But...

How many frauds were detected?

```text
0
```

The model is completely useless.

---

## Why?

Because fraud is very rare.

The model learned

> "If I always predict Genuine, I'm correct 99% of the time."

Accuracy doesn't punish this enough.

---

# Better Metrics

Instead of accuracy, use:

* Precision
* Recall
* F1-score
* ROC-AUC

---

## Precision

> Of everything predicted as positive, how many were actually positive?

Formula

[
Precision=\frac{TP}{TP+FP}
]

Example

Predicted Fraud = 20

Actual Fraud = 15

```text
Precision = 15/20 = 75%
```

---

## Recall

> Of all actual positives, how many did we find?

Formula

[
Recall=\frac{TP}{TP+FN}
]

Suppose

Actual fraud = 10

Detected fraud = 8

Recall

```text
8/10 = 80%
```

---

## F1 Score

Sometimes

High precision

Low recall

or

High recall

Low precision

F1 balances both.

Formula

[
F1=\frac{2PR}{P+R}
]

It is the **harmonic mean** of precision and recall.

---

### Example

Model A

```text
Precision = 100%

Recall = 20%
```

Model B

```text
Precision = 70%

Recall = 75%
```

Even though Model A has perfect precision, it misses most fraud cases.

Model B usually has a much higher F1 score because it balances both.

---

## ROC-AUC

ROC measures

> How well can the model distinguish between classes?

AUC ranges

```text
0.5  → Random guessing

0.7  → Fair

0.8  → Good

0.9+ → Excellent

1.0  → Perfect
```

Unlike accuracy, AUC evaluates the model across **all possible classification thresholds**, not just one threshold like 0.5.

---

## Interview Insight

For imbalanced datasets

Never say

> My model has 99% accuracy.

Instead say

> Since the data is imbalanced, I evaluated using Precision, Recall, F1-score, and ROC-AUC because they better reflect minority-class performance.

# 2. `class_weight='balanced'`

Many sklearn models support

```python
class_weight="balanced"
```

Examples:

```python
LogisticRegression(class_weight="balanced")

DecisionTreeClassifier(class_weight="balanced")

RandomForestClassifier(class_weight="balanced")
```

---

## What problem does it solve?

Suppose

```text
Healthy : 900

Cancer : 100
```

Normally

Each mistake has equal importance.

Misclassifying

1 healthy patient

=

1 cancer patient

But that's usually not what we want.

Missing cancer is much more serious.

---

## How does sklearn fix this?

It automatically gives **higher weight to the minority class** and **lower weight to the majority class**.

The formula used is

[
\text{weight}_i =
\frac{\text{Number of samples}}
{\text{Number of classes} \times \text{Samples in class}_i}
]

---

### Example

Dataset

```text
Healthy = 900

Cancer = 100

Total = 1000
```

Weight for Healthy

[
\frac{1000}{2\times900}
=======================

0.56
]

Weight for Cancer

[
\frac{1000}{2\times100}
=======================

5
]

So during training

```text
One Cancer sample

≈

Nine Healthy samples
```

The model is penalized much more for misclassifying a cancer case.

---

## Intuition

Imagine a teacher grading exams.

Normally

Every mistake loses

```text
1 mark
```

Balanced weighting says

```text
Mistake on rare class

Lose 10 marks
```

Now the model pays much more attention to rare examples.

---

## Example

Without balancing

```text
Healthy Accuracy = 99%

Cancer Accuracy = 30%
```

With

```python
class_weight="balanced"
```

You may get

```text
Healthy Accuracy = 95%

Cancer Accuracy = 80%
```

Overall accuracy drops slightly, but the model becomes much more useful.

# 3. SMOTE (Synthetic Minority Oversampling Technique)

Instead of changing the loss function, SMOTE changes the **training data**.

---

## Problem

Suppose

```text
Class A = 1000 samples

Class B = 100 samples
```

The model barely sees Class B.

---

### Random Oversampling

One solution

Duplicate minority samples.

Example

Original

```text
B1
B2
B3
```

After duplication

```text
B1
B2
B3
B1
B2
B3
B1
B2
```

Problem

The model may simply memorize these repeated examples, leading to overfitting.

---

## SMOTE Idea

Instead of copying

Create **new synthetic samples**.

Suppose two minority samples are

```
Point A = (2,3)

Point B = (6,5)
```

SMOTE chooses a random point **between them**.

Example

```
New Point

(4,4)
```

Now instead of

```
A

B
```

we have

```
A

New Sample

B
```

The minority class becomes denser and more diverse.

---

## Visual

Original

```text
● ● ● ● ● ● ● ●

        ○
             ○
```

After SMOTE

```text
● ● ● ● ● ● ● ●

     ○ ○ ○ ○ ○
```

The minority region is better represented.

---

# How does SMOTE work?

For each minority sample

1. Find its **k nearest minority neighbors** (default `k=5`).
2. Randomly choose one neighbor.
3. Draw a line between the two samples.
4. Pick a random point along that line.
5. Add that point as a new synthetic sample.

This process repeats until the desired class balance is reached.

---

## Example

Minority sample

```
(2,3)
```

Nearest neighbor

```
(6,5)
```

Difference

```
(4,2)
```

Choose a random number

```
0.5
```

New point

```
(2,3) + 0.5 × (4,2)

=

(4,4)
```

The new sample lies **between** existing minority samples rather than being an exact duplicate.

---

# Implementation with `imbalanced-learn`

Install

```bash
pip install imbalanced-learn
```

---

### Code

```python
from imblearn.over_sampling import SMOTE

smote = SMOTE(random_state=42)

X_train_smote, y_train_smote = smote.fit_resample(
    X_train,
    y_train
)
```

Notice

Use

```python
fit_resample()
```

instead of

```python
fit_transform()
```

because SMOTE changes both the features and the labels.

---

## Before SMOTE

```text
Class 0 : 900

Class 1 : 100
```

After SMOTE

```text
Class 0 : 900

Class 1 : 900
```

Now both classes have equal representation in the training data.

---

# Important Rule

**Apply SMOTE only to the training set.**

Correct workflow

```text
Dataset
      │
      ▼
Train/Test Split
      │
      ├──────────► Test Set (untouched)
      │
      ▼
Apply SMOTE ONLY on Training Set
      │
      ▼
Train Model
      │
      ▼
Evaluate on Original Test Set
```

### Why?

If you apply SMOTE **before** splitting the data, synthetic samples generated from training examples can end up in the test set (or vice versa). This leaks information from training into testing and produces overly optimistic results.

---

# When to Use Each Technique

| Technique                     | What it does                                           | Advantages                                       | Limitations                                                                 |
| ----------------------------- | ------------------------------------------------------ | ------------------------------------------------ | --------------------------------------------------------------------------- |
| **F1-score / ROC-AUC**        | Better evaluation metrics                              | Reflect minority-class performance               | Don't fix the imbalance themselves                                          |
| **`class_weight='balanced'`** | Gives higher penalty to mistakes on the minority class | Very easy to use, no data modification           | Not supported by every model and may reduce majority-class accuracy         |
| **SMOTE**                     | Generates synthetic minority samples                   | Helps the model learn a richer decision boundary | Can create noisy samples if classes overlap; apply only to the training set |

---

# Which Should You Use?

There isn't a single "best" solution.

* **Mild imbalance (e.g., 60:40 or 70:30):** Often, using appropriate metrics is enough.
* **Moderate imbalance (e.g., 90:10):** Try `class_weight='balanced'` first because it's simple and doesn't change the data.
* **Severe imbalance (e.g., 99:1):** Consider SMOTE (or related techniques) together with proper evaluation metrics like F1 and ROC-AUC.

In practice, data scientists often compare several approaches using **cross-validation** and choose the one that gives the best **F1-score** or **ROC-AUC** on the validation data, then evaluate the final model once on the untouched test set.
